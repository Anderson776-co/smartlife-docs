# ADR-0022 — Seleccionar plataforma de despliegue del frontend

***Estado:** Aprobada
**Fecha:** 20-09-2026

## Contexto

SmartLife requiere desplegar el frontend de la PWA garantizando disponibilidad, bajos tiempos de carga y CI/CD sencillo de operar.

## Escenarios de calidad y funcionalidades significativas referenciados

No aplica

## Decisión

C. Google Cloud Platform (Firebase Hosting): Se selecciona Firebase Hosting, el servicio de alojamiento de contenido estático de Google Cloud Platform, como plataforma de despliegue del frontend de SmartLife. El criterio principal es la consolidación del sistema en un único proveedor de nube: GCP ya fue seleccionado como entorno de despliegue del backend (ADR-0023) y concentra la mayoría de los componentes externos que adoptará la aplicación, como el proveedor de identidad Firebase Authentication (ADR-0001), el gestor de secretos Google Secret Manager (ADR-0029), la observabilidad con Google Cloud Managed Service for Prometheus, Cloud Logging y Cloud Trace (ADR-0030) y el punto de entrada de la API con Google Cloud API Gateway (ADR-0033). Dado que todo proyecto de Firebase es al mismo tiempo un proyecto de Google Cloud, el frontend queda alojado en el mismo proyecto, con la misma consola, la misma facturación y el mismo modelo de identidad y permisos (IAM) que el resto de la arquitectura, sin dar de alta un proveedor adicional exclusivamente para servir archivos estáticos.

Esta consolidación no implica renunciar a las capacidades que hacían atractivas a las plataformas especializadas. Firebase Hosting distribuye el contenido mediante una CDN global con certificado SSL gratuito para dominios personalizados, y su integración oficial con GitHub Actions despliega automáticamente cada Pull Request en un canal de vista previa (preview channel) con una URL temporal para revisión, y publica en el canal en vivo cuando el cambio se fusiona a la rama principal. De esta manera se conserva el mismo flujo de trabajo que ofrecía Vercel (despliegue por push y previews por Pull Request), sin mantener scripts de despliegue propios. Además, el compilado de Angular es un conjunto de archivos estáticos que Firebase Hosting sirve de forma nativa, configurando únicamente la reescritura de rutas hacia index.html para el enrutamiento del lado del cliente. En costos, Firebase Hosting incluye sin cargo 10 GB de almacenamiento y 360 MB diarios de transferencia; como el proyecto ya opera bajo el modelo de pago por uso de GCP, se mantienen esas mismas cuotas gratuitas y solo se cobra el excedente (0,15 USD por GB transferido), un volumen acorde con la concurrencia mensual y predecible de una unidad residencial.

Frente a Vercel (opción A), se descarta porque, aunque ofrece CDN global, CI/CD automático y previews por Pull Request con muy poca configuración, introduciría un proveedor externo adicional fuera del ecosistema de GCP donde se despliegan el backend y los demás componentes del sistema, con su propia consola, facturación y modelo de acceso a monitorear. Adicionalmente, su compatibilidad de referencia está orientada al ecosistema React/Next.js, ventaja que dejó de aplicar al seleccionar Angular como framework del frontend (ADR-0021). Su plan gratuito (Hobby) está limitado a uso no comercial, por lo que la operación productiva de la aplicación exigiría el plan de pago por miembro del equipo, mientras que en GCP el costo del frontend se suma al consumo ya facturado del proyecto.

Frente a Cloudflare Pages (opción B), aunque Cloudflare ya es un proveedor del proyecto por Cloudflare R2 (ADR-0002) y Cloudflare WAF (ADR-0024), y ofrece CI/CD por Git y CDN integrada de forma similar a Firebase Hosting, se descarta porque Cloudflare cumple en la arquitectura un rol perimetral y de almacenamiento, no de entorno de ejecución. Alojar el frontend allí separaría los componentes desplegables del sistema en dos nubes distintas (frontend en Cloudflare, backend en GCP), dispersando los pipelines de despliegue, la gestión de entornos y la trazabilidad de las versiones publicadas.

Frente a Google Cloud Storage + Cloud CDN (opción D), aunque también pertenece a GCP y ofrece mayor control sobre la configuración de caché y del balanceador, se descarta porque exige aprovisionar y mantener un bucket con alojamiento de sitio web, un balanceador de carga HTTP(S) externo y la configuración de Cloud CDN, además de construir un pipeline propio que compile y suba los archivos en cada cambio, sin previews por Pull Request de fábrica. Ese esfuerzo de configuración no se justifica para un frontend estático y un equipo reducido, cuando Firebase Hosting entrega las mismas capacidades de distribución dentro del mismo proyecto de GCP sin infraestructura adicional que administrar.

En conclusión, Firebase Hosting sobre GCP se considera la alternativa más adecuada para el despliegue del frontend de SmartLife, ya que unifica el frontend con el backend y con los servicios transversales adoptados en un solo proveedor, proyecto y modelo de facturación, mientras conserva la CDN global, el CI/CD automático y las vistas previas por Pull Request que exige el contexto con el menor esfuerzo operativo para el equipo.

## Opciones consideradas

- A. Vercel: Plataforma de despliegue de frontend con CDN global integrada, CI/CD automático por cada push a Git y previews automáticos por Pull Request. Compatibilidad de referencia con proyectos React/Next.js. Su plan gratuito (Hobby) está limitado a uso no comercial; es un proveedor externo al entorno de GCP donde se despliega el backend.
- B. Cloudflare Pages: Plataforma de despliegue de frontend del mismo proveedor ya elegido para almacenamiento de objetos (Cloudflare R2) y protección perimetral (Cloudflare WAF), con CDN global integrada y CI/CD automático por Git. Separa el frontend del entorno de ejecución del backend en GCP.
- C. Google Cloud Platform (Firebase Hosting): Servicio de alojamiento de contenido estático de GCP, dentro del mismo proyecto que el backend y los servicios transversales, con CDN global, SSL gratuito para dominios personalizados, integración oficial con GitHub Actions y canales de vista previa por Pull Request. Incluye 10 GB de almacenamiento y 360 MB/día de transferencia sin costo.
- D. Google Cloud Storage + Cloud CDN: Bucket de Cloud Storage configurado como sitio web estático detrás de un balanceador de carga HTTP(S) con Cloud CDN. Ofrece control granular de caché y red, pero no incluye CI/CD ni previews de fábrica y requiere aprovisionar y mantener la infraestructura de entrega.

## Consecuencias positivas

- Consolidación en un solo proveedor de nube: El frontend, el backend y los servicios transversales (identidad, secretos, observabilidad y API Gateway) comparten el mismo proyecto, consola, facturación y modelo de permisos IAM de GCP.
- Sinergia con Firebase Authentication: El frontend queda alojado en el mismo proyecto de Firebase que ya provee la autenticación (ADR-0001), aprovechando el ecosistema adoptado desde esa decisión.
- CI/CD sin configuración manual compleja: La integración oficial con GitHub Actions despliega automáticamente a producción al fusionar cambios en la rama principal.
- Previews automáticos por Pull Request: Cada Pull Request se publica en un canal de vista previa con URL temporal, facilitando la revisión antes de fusionar.
- CDN y SSL incluidos: La distribución global y los certificados para dominios personalizados reducen los tiempos de carga sin configurar infraestructura adicional.
- Costo acorde al volumen actual: Las cuotas sin costo de almacenamiento y transferencia cubren el tráfico inicial, y el excedente se factura dentro del mismo consumo del proyecto en GCP.

## Consecuencias negativas

- Mayor dependencia de GCP: Al concentrar frontend, backend y servicios transversales en un mismo proveedor, una interrupción o un cambio en sus condiciones comerciales impacta a todo el sistema a la vez.
- Coordinación con Cloudflare WAF: El dominio personalizado debe verificarse en Firebase Hosting mientras el tráfico pasa por el proxy de Cloudflare (ADR-0024), lo que puede requerir desactivar temporalmente el proxy para emitir el certificado SSL y ajustar la configuración de caché para evitar duplicidad entre ambas CDN.
- Previews con menos integración que Vercel: Los canales de vista previa dependen de la configuración del flujo de GitHub Actions, frente a la experiencia completamente integrada en la interfaz que ofrece Vercel.
- Alcance limitado a contenido estático: Si en el futuro se adopta renderizado del lado del servidor (Angular SSR), será necesario evaluar Firebase App Hosting o Cloud Run, con un modelo de costos distinto.
