# Prueba de Concepto — ADR-0029

## Objetivo

Validar que Google Secret Manager permite almacenar secretos de forma segura sobre la cuenta de GCP ya contratada, que soporta versionado ante rotación de credenciales, y que registra automáticamente un log de auditoría de cada operación realizada sobre un secreto.

## Métricas y resultados

Se creó el proyecto smartlife-poc-secrets en Google Cloud Platform y se habilitó la Secret Manager API (confirmado: "Estado: Habilitada"). Se creó un secreto llamado wompi-llave-privada con un valor de ejemplo simulando la llave privada de la pasarela de pagos, obteniendo confirmación "Se creó el secreto 'wompi-llave-privada'" y una primera versión (Versión 1) con estado "Habilitada", encriptación "Administrada por Google". Se creó una segunda versión del mismo secreto con un valor distinto, simulando una rotación de credenciales; el panel de "Versiones" mostró ambas versiones (1 y 2) simultáneamente disponibles, cada una con su propia fecha de creación exacta (8:26 a.m. y 8:28 a.m. respectivamente), sin que la creación de la nueva versión eliminara o sobrescribiera la anterior. Al consultar la pestaña "Registros" del secreto, se encontró un registro de auditoría automático con tres entradas correspondientes a las operaciones realizadas: CreateSecret (creación del secreto) y dos entradas AddSecretVersion (una por cada versión creada), cada una con su fecha y hora exacta, sin que se hubiera configurado manualmente ningún sistema de logging adicional.

## Conclusiones

La PoC valida los tres criterios centrales de la decisión: Secret Manager opera correctamente sobre la cuenta de GCP ya usada para otros servicios transversales del proyecto, sin necesidad de dar de alta un proveedor adicional; el versionado funciona tal como lo documenta Google, conservando el historial completo de valores de un secreto ante una rotación en lugar de sobrescribirlo, lo cual permitiría revertir a una versión anterior si una rotación introdujera un error; y el registro de auditoría se genera de forma automática y nativa por cada operación (creación y nuevas versiones), sin configuración adicional por parte del equipo, respaldando directamente los requisitos de auditabilidad que el proyecto prioriza. Se confirmó también, como parte del proceso mismo, la consecuencia negativa ya anticipada de la curva de configuración: habilitar la API exigió activar la facturación del proyecto con una tarjeta de verificación antes de poder usar el servicio, aunque la operación completa permaneció dentro del nivel gratuito sin generar ningún cargo. Queda fuera del alcance de esta prueba la configuración de permisos IAM granulares por servicio (aquí se operó con la cuenta con permisos de administrador completo), la integración real desde una aplicación Spring Boot consultando el secreto en tiempo de ejecución, y la medición de la latencia de red al consultar el secreto en lugar de una variable de entorno ya cargada en memoria.
